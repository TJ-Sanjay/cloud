UIT2702 — EXERCISE 7
HYPERVISOR CLUSTERING IN A CLOUD ENVIRONMENT
=============================================

AIM
---
Set up two hypervisor hosts, join them into a cluster, verify communication and cluster membership, and examine high availability and workload balancing.

IMPORTANT BEFORE STARTING
-------------------------
This exercise is performed mainly in VMware Workstation and the hypervisor web interface, not by running a Python program. Nested virtualization requires hardware virtualization support and enough host resources.

The lab manual suggests two hypervisor VMs with around 2 CPUs and 8 GB RAM each. This can be demanding on a student laptop. If your host cannot run two nested hypervisors, reduce resources only if the chosen hypervisor supports it, or perform the lab on a suitable lab machine. Do not claim a working cluster unless both nodes actually join and the cluster status verifies it.

PART 1 — CREATE THE HYPERVISOR HOSTS
------------------------------------

STEP 1: Check host virtualization support.
Make sure CPU virtualization is enabled in the computer's BIOS/UEFI. In VMware Workstation, the VM must support nested virtualization.

STEP 2: Create the first hypervisor VM.
In VMware Workstation:
1. Select File > New Virtual Machine.
2. Choose the installer ISO for a supported hypervisor, such as Proxmox VE.
3. Name the VM Hypervisor1.
4. Allocate suitable CPU, RAM, and disk resources. The lab manual suggests approximately 2 CPUs and 8 GB RAM per host.
5. Enable the VMware option to virtualize Intel VT-x/EPT or AMD-V/RVI, if available.
6. Configure its network adapter so it can communicate with the second hypervisor VM.

STEP 3: Create the second hypervisor VM.
Repeat Step 2 using the same supported hypervisor version. Name it Hypervisor2. Give it its own unique hostname and network address.

STEP 4: Choose a network mode.
The lab manual suggests Bridged networking so the VMs share the host's network. If your network does not permit bridged devices, use a suitable private VMware network for both nodes and ensure each node can reach the other. Both hypervisor nodes must be on a mutually reachable network; do not expose management interfaces to the public internet.

STEP 5: Install the hypervisor on each VM.
Boot each VM from its installer ISO and complete the installation. Set a strong root/admin password and a unique hostname for each host. Configure a static IP address for each host and note:
    Hypervisor1 IP: ____________________
    Hypervisor2 IP: ____________________

STEP 6: Open each hypervisor's management interface.
Use the management URL shown by the hypervisor installer/console. For Proxmox VE, the web interface is normally:
    https://HYPERVISOR_IP:8006

Replace HYPERVISOR_IP with the correct host IP. Accept a self-signed certificate warning only if you are sure you are connecting to your own lab host.

PART 2 — VERIFY NETWORK CONNECTIVITY
------------------------------------

STEP 7: Open a shell/console on each hypervisor.
On Proxmox VE, use the web interface's node shell or the VM console.

STEP 8: Check hostname and network addresses.
Run on each node:
    hostname
    ip addr

STEP 9: Test connectivity between nodes.
From Hypervisor1, run:
    ping -c 4 HYPERVISOR2_IP

From Hypervisor2, run:
    ping -c 4 HYPERVISOR1_IP

Replace the placeholders with actual IPs. If ping fails, check IP settings, network mode, routing, firewall, and hostname resolution before continuing.

STEP 10: Ensure the hostnames resolve consistently.
Configure DNS or the hosts file on both nodes if required by the selected hypervisor. Use the actual names and IP addresses. Do not use duplicate hostnames or duplicate IP addresses.

PART 3 — CREATE AND JOIN THE CLUSTER (PROXMOX EXAMPLE)
------------------------------------------------------

STEP 11: Create the cluster on Hypervisor1.
In the Proxmox web interface:
1. Select Datacenter.
2. Open Cluster.
3. Choose Create Cluster.
4. Enter a unique cluster name, for example cloud-lab.
5. Select the intended cluster network/link address.
6. Create the cluster and wait for the operation to finish.

STEP 12: Obtain the join information.
On Hypervisor1, open Datacenter > Cluster and inspect the Join Information. Copy the join details shown by that host. Keep the join secret private.

STEP 13: Join Hypervisor2 to the cluster.
On Hypervisor2, open Datacenter > Cluster > Join Cluster (wording can vary by version). Enter the join information from Hypervisor1 and authenticate using the appropriate credentials. Confirm the node names and IP addresses before joining.

IMPORTANT: Use the join information generated by your own Hypervisor1. Do not reuse another person's join command or an example from the internet. Follow the UI for your installed Proxmox version.

STEP 14: Verify the cluster.
In the Proxmox web interface, open Datacenter > Cluster and confirm both Hypervisor1 and Hypervisor2 appear as cluster members. Check node status and cluster communication.

If a CLI verification is supported by your installed Proxmox version, run on a node:
    pvecm status
    pvecm nodes

Do not proceed until the cluster status is healthy and both nodes are visible.

PART 4 — HIGH AVAILABILITY (ONLY IF SUPPORTED)
----------------------------------------------

STEP 15: Check cluster quorum first.
A two-node cluster can lose quorum when one node fails. Check the cluster status and follow the hypervisor's supported quorum guidance before configuring HA. A third vote or quorum device may be required. Never force quorum blindly; it can risk data integrity.

STEP 16: Check storage requirements.
Automatic VM restart or migration requires storage and configuration supported by your hypervisor. Verify whether the test VM's disk is accessible to the other node. Do not assume local storage on one host is automatically available to the other.

STEP 17: Create a small test VM.
In the cluster manager, create a small test VM on the cluster. Confirm that its configuration appears in the cluster view. Use a harmless test workload.

STEP 18: Configure HA only if the prerequisites are met.
In the management interface, open the High Availability section and add the test VM as an HA resource according to the installed hypervisor's documentation. Do this only after quorum and storage requirements have been met.

STEP 19: Test the HA behavior carefully.
If your setup supports HA, follow the hypervisor's documented test procedure and verify whether the VM restarts on another node when a host fails. A two-node lab without proper quorum/storage may not support this test safely. If prerequisites are unavailable, document that limitation rather than claiming successful automatic failover.

PART 5 — LOAD BALANCING / RESOURCE DISTRIBUTION
------------------------------------------------

STEP 20: Inspect resource utilization.
In the hypervisor dashboard, compare CPU and memory usage on both nodes. Run a harmless workload inside a test VM if needed.

STEP 21: Review migration or balancing options.
Check the hypervisor's supported migration, scheduling, and resource-balancing policies. If shared storage and the correct licensing/configuration are available, perform a supported VM migration test. Do not assume all hypervisors automatically balance workloads or move VMs based only on CPU usage.

STEP 22: Verify and record the results.
Capture the cluster membership view, node health, resource usage, test VM visibility, and any migration/HA test that your configuration actually supports.

TROUBLESHOOTING
---------------
- Nested virtualization unavailable: check BIOS/UEFI virtualization and VMware nested-virtualization settings.
- Nodes cannot communicate: verify static IPs, subnet, network mode, firewall, DNS/hosts entries, and time synchronization.
- Node cannot join: verify cluster join information, version compatibility, unique hostnames, and correct management addresses.
- Cluster loses quorum: stop and investigate quorum requirements. Do not force quorum without understanding the risks.
- High resource usage: shut down nested hypervisor VMs when the exercise is complete.

RESULT / EVIDENCE
-----------------
1. VMware Workstation showing both hypervisor VMs.
2. Management interface for each hypervisor.
3. Successful ping tests between nodes.
4. Cluster dashboard showing both nodes.
5. Cluster status output, if supported.
6. Test VM visible in the cluster.
7. HA/migration evidence only if those features were actually configured and tested.

NOTE
----
The exact UI and commands vary between Proxmox VE, ESXi, and their versions. These steps use Proxmox VE as the concrete example, matching the lab manual's cluster-creation flow.
